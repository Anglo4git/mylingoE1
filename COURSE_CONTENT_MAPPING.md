# Mylingo — Course Content Mapping (Agent 74)

## Objective

Map every existing quiz in `master_source.csv` into the
Course → Unit → Lesson shape defined by Agent 73
(`COURSE_SCHEMA.md` / `course_schema.py`), deterministically and without
duplicating any question/answer content.

## Mapping rule

1. **One course per CEFR level.** `course-a1` … `course-c2`. A level with
   no published quizzes yet simply has no course (none currently — all
   six levels have published content).
2. **One unit per (level, quiz_category) bucket that exists in the
   catalog**, in the fixed order `Grammar, Vocabulary, Writing, Academic
   English`. This introduces no new grouping concept — it is exactly the
   19 level+category buckets `production_quiz_profiles.json` already
   names and packs (Agents 16/81). Unit title = the category name.
3. **One lesson per quiz**, ordered by ascending `quiz_id` within its
   unit. `lesson.title = quiz.title`, `lesson.category = quiz.quiz_category`,
   `lesson.exercise_quiz_ids = [quiz_id]` (single-quiz lessons).
4. **`lesson.revision.summary` = the quiz's own `description` field**,
   reused verbatim. This is already-published editorial metadata (e.g.
   `"Practice Present Simple."`), not question/answer content, so reusing
   it is not a duplication of exercise content.
5. Only rows with `status == "published"` in `master_source.csv` are
   mapped. A non-published quiz is neither mapped nor built into
   `course_content/` — it stays fully intact and reachable through the
   legacy quiz routes, it just isn't yet part of the course/journey layer.

### Why 1:1 (one quiz per lesson) instead of clustering multiple quizzes into one topic lesson

The handoff's worked example (`Daily Routines` combining an
Adverbs-of-Frequency-style quiz and a Vocabulary quiz) implies
hand-curated topic clusters. That kind of clustering requires an
editorial judgment call per topic — genuinely useful, but not
*deterministic*: two people (or two runs) would group differently, which
violates the "deterministic mapping layer" requirement and this agent's
guardrail against inventing content decisions. One-quiz-per-lesson is the
mapping that requires no editorial judgment at all: every published quiz
already has an unambiguous `(level, quiz_category, quiz_id)`, so the
lesson it belongs in is fully determined by data already in
`master_source.csv`. Hand-curated multi-quiz topic lessons (the richer
`Daily Routines`-style experience) remain possible later — a future
agent can re-cluster specific lessons' `exercise_quiz_ids` without
changing the schema, since `Lesson.exercise_quiz_ids` already accepts
more than one ID (Agent 73's contract, and this mapping's own
`a2-007`/`a2-010` two-quiz sample from the prior milestone, exercised
that). This pass just doesn't invent which quizzes belong together.

### Known limitation (explicitly out of scope here)

`revision.summary` is reused from the quiz's one-line `description`
field, which is generic (`"Practice X."`). This satisfies the schema
(a non-empty, brief, non-fabricated summary) and gives every lesson a
real skippable revision step, but it is **not** the richer explanation +
examples + key-terms revision the handoff envisions (e.g. "We use the
present simple for regular routines... always · usually · sometimes ·
never"). Authoring that richer per-topic revision content is a
pedagogical content task, not a mapping task — doing it here would mean
inventing 60 grammar/vocabulary explanations without a subject-matter
review step, which risks introducing incorrect teaching content at
scale. `revision.examples` and `revision.key_terms` are left unset
(both optional in the schema) rather than fabricated. Flagged here for
whichever agent/process owns content authoring next.

## Files delivered

- `map_quiz_catalog.py` — deterministic, idempotent generator. Reads
  `master_source.csv` (read-only), writes
  `course_content/{courses,units,lessons}.json`. Re-running it against
  an unchanged catalog produces byte-identical output (see
  `test_mapping_is_deterministic_across_runs`).
- `audit_course_mapping.py` — the orphan/reference/level/category audit
  described above. Exit code `0` = clean, `1` = problems found (printed).
- `course_content/{courses,units,lessons}.json` — regenerated to cover
  the full catalog (60 quizzes), replacing Agent 73's single-lesson
  sample. Still validates clean against `course_schema.py`.
- `test_course_content_mapping_agent74.py` — 9 unittest cases: full
  catalog coverage (every published quiz mapped exactly once, no
  non-published quiz mapped), unit-grouping correctness, output
  validates clean, determinism across runs, shipped JSON matches a
  fresh generation (drift guard), and two negative tests that plant a
  synthetic orphan-quiz bug and a synthetic wrong-level bug and confirm
  the audit catches both.

## Guardrails honored

- ✅ Did not rewrite any quiz content — every quiz row in
  `master_source.csv` is byte-for-byte unchanged.
- ✅ Did not create a duplicate exercise engine — lessons hold
  `exercise_quiz_ids` references only.
- ✅ Did not silently discard any quiz — all 60 published quizzes are
  mapped; 0 are orphaned; the audit fails loudly (exit 1) if that ever
  stops being true.
- ✅ Existing quiz IDs and routes are untouched — nothing under `site/`
  was modified.
- ✅ Mapping is deterministic — same `master_source.csv` in, same
  `course_content/*.json` out, every time (test-covered).

## Handoff to Agent 75 (Course Landing Page)

- `course_content/courses.json` now has all 6 levels, each with
  `status: "published"` and a non-empty `unit_ids` — safe to build
  `/courses/` and course landing pages against real data immediately,
  no placeholder/mock content needed.
- Each course's `unit_ids` → unit → `lesson_ids` → lesson chain is fully
  populated and pre-validated; lesson counts and exercise counts per
  course/unit are derivable directly from array lengths
  (`len(unit_ids)`, `len(lesson_ids)`, `len(exercise_quiz_ids)`)
  without any additional lookups.
- Course pages must still work if a learner skips the journey (per the
  original handoff) — nothing about this mapping assumes sequential
  unit/lesson traversal; every lesson is independently addressable by
  `lesson_id` and independently resolves to its quiz(zes) via
  `exercise_quiz_ids`.
- Re-run `python3 map_quiz_catalog.py` any time `master_source.csv`
  gains new published quizzes, then `python3 audit_course_mapping.py`
  to re-confirm zero orphans before shipping — do not hand-edit
  `course_content/*.json` (the drift-guard test
  `test_shipped_content_matches_fresh_generation` will fail CI if the
  checked-in JSON and a fresh generation diverge).
- If/when hand-curated multi-quiz topic lessons are wanted (the
  "Daily Routines" style example from the original handoff), that is a
  content-authoring change to specific lessons'
  `title`/`category`/`exercise_quiz_ids`, not a schema or mapping-rule
  change — `course_schema.py` already supports it.
