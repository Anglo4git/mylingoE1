### 2 new equivalents confirmed — one guard-redundant-by-type variant, one genuinely new class

| Location | Mutation tried | Result | Why it's equivalent |
|---|---|---|---|
| `decideAssessmentPath` (~138) | Changed `if (confidence !== 'high' && secondary === estimated) secondary = adjacentLevel(estimated, -1);` to `if (secondary === estimated) secondary = adjacentLevel(estimated, -1);`, dropping the `confidence !== 'high' &&` clause | **953 passed, 1 failed (identity only) → equivalent** | When `confidence === 'high'`, `secondary` was just set to `null` on the line above. `null === estimated` is always `false` because `normalizeLevel` only ever returns a string (one of `LEVELS` or `'a1'`), never `null`. So the dropped clause and the type mismatch it was guarding against produce the identical result — the reassignment branch simply never fires when `secondary` is `null`, with or without the explicit `confidence` check. **New sub-pattern: a boolean guard made redundant not by an earlier branch's value (Class B) or a same-value reassignment (Class A), but by a downstream equality check that can never match across two different JS types (string vs. `null`) — a type-level variant of Class B.** |
| `validatePlacementBlueprint` (~436) | Dropped the first validation line entirely: `if (b.version !== 2) return false;` | **953 passed, 1 failed (identity only) → equivalent** | Checked `tests/run.js` for every call site: `validatePlacementBlueprint()` is invoked exactly twice, both times with no arguments against the module's own hardcoded `PLACEMENT_BLUEPRINT_V2` constant, and both assertions only check that it returns `true` (`assert.strictEqual(P.validatePlacementBlueprint(), true)`) — there is no test anywhere that constructs a malformed blueprint to exercise any `return false` branch. Since the constant always satisfies `b.version === 2`, removing that check cannot change any observed return value under this suite. **New class, distinct from every prior pattern: a self-validation function whose guard clauses check invariants of a hardcoded constant the function always receives — every `return false;` line in this function is individually "equivalent" under the current suite for the same reason, not because of redundant logic but because the false path is structurally unreachable in every existing test. This is a caution, not a green light: unlike Class A/B (truly redundant code), removing any of these checks is a real regression in intent (it would silently stop catching a corrupted blueprint at dev time) even though today's tests can't tell the difference. Flagging as equivalent-under-suite only, not recommending removal.** |
